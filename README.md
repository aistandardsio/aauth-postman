# AAuth Postman Collection

Postman collections for [AAuth](https://datatracker.ietf.org/doc/draft-hardt-oauth-aauth-protocol/) (draft-hardt-oauth-aauth-protocol-11): every access mode as a folder of requests you can send, from agent identity to federated authorization, with values passed from each response to the next request and checks on every response.

## How It Works

- **Generated, not hand-written.** The collection is generated by [PIDL](https://github.com/grokify/pidl) from the AAuth protocol document in [agent-protocols](https://github.com/aistandardsio/agent-protocols), the same document behind its AAuth walkthrough, so the requests, order and checks match the walkthrough step for step. Edit the protocol document, not the collection.
- **Postman plays the agent.** The agent provider, resource, person server and access server are real servers: the [AAuth sandbox](https://github.com/aauth-dev/aauth-go) from aauth-go runs them all, on a laptop, in Docker or on Kubernetes.
- **Signing happens outside Postman.** Every AAuth request carries an HTTP message signature (RFC 9421). Requests go through the sandbox's signing helper, which signs them with the agent's key and forwards them.

## Layout

| Path | Contents |
|------|----------|
| `collections/` | Generated collections: AAuth's access modes, signed (against the sandbox) and mock (saved example responses), and the Petstore |
| `environments/` | Generated environments: the sandbox, the Petstore behind it, and a Postman mock server |
| `pidl/` | The documents the collections are generated from: what the sandbox's resources and the Petstore perform, each extending the AAuth document |
| `bindings/` | How the sandbox and the Petstore map to the AAuth document's roles, for comparing a run with it |
| `docs/` | Setup guide and [interop testing runbook](docs/interop.md) |

## Quick Start

The setup has two parts, so each can be run and studied on its own. With Docker, and the checkouts below in the `~/go/src/github.com/<org>/<repo>` layout until the images are published:

**Part 1: the AAuth sandbox.** The agent provider, person server and access server, with the demo resources of [aauth-go](https://github.com/aauth-dev/aauth-go). It needs only an aauth-go checkout, at `../../aauth-dev/aauth-go`.

```bash
docker compose up -d --build --wait             # the sandbox: every role and the signing helper
docker compose --profile test run --rm newman   # run every access mode with Newman
```

**Part 2: the Petstore resource server.** The [Petstore](https://github.com/grokify/petstore) as a resource server of its own, behind the sandbox. It also needs a petstore checkout (v0.2.0 or later), at `../../grokify/petstore`.

```bash
docker compose --profile petstore up -d --build --wait      # adds the Petstore
docker compose --profile petstore run --rm newman-petstore  # the Petstore collection
```

`make test-docker` runs both parts. To start over, or to make the Petstore's pets available to order again, recreate the sandbox and the Petstore together (`docker compose --profile petstore up -d --wait --force-recreate sandbox petstore`): the Petstore creates a new signing key each time it starts, and the sandbox's person server keeps the key it saw.

In Postman, import `collections/aauth.postman_collection.json` and `environments/sandbox.postman_environment.json`, select the environment, and run a folder. Postman talks only to the signing helper at `http://127.0.0.1:8099`, so no hosts entries or certificates are needed.

Without Docker, run the sandbox from aauth-go with `go run ./cmd/aauth-sandbox serve`; see [docs/setup.md](docs/setup.md). To test an agent, resource or person server of your own, see the [interop testing runbook](docs/interop.md). Every sandbox option is in the [aauth-go sandbox guide](https://aauth-dev.github.io/aauth-go/guides/sandbox/).

## The Petstore, Two Ways

The [Swagger Petstore](https://github.com/grokify/petstore) runs next to the sandbox as an AAuth resource at `https://petstore.aauth.test`. Browsing needs only the agent's identity; placing an order needs the person's approval for `write:orders`. Two demos play the agent against the same servers, so they send the same messages:

| Demo | The agent | Run it |
|------|-----------|--------|
| Postman | Postman, one step per request | `collections/petstore.postman_collection.json` with `environments/petstore.postman_environment.json`, or `docker compose --profile petstore run --rm newman-petstore` |
| omniagent | [omniagent](https://github.com/plexusone/omniagent), an AI agent whose tools are the Petstore's operations | `ANTHROPIC_API_KEY=... docker compose --profile petstore run --rm omniagent` |

In the Postman folder each challenge is a request you can inspect: the order is refused with `requirement=person-token`, then with `requirement=auth-token` and a resource token, the person server asks the person to approve, and the order goes through with the auth token. omniagent does the same steps inside its HTTP client and prints the approval link. Compare them in the sandbox's trace:

```bash
docker compose exec sandbox aauth-sandbox trace --state /state
```

The omniagent container also needs an omniagent checkout at `../../plexusone/omniagent`, until its image is published. Set `AAUTH_GO_DIR`, `PETSTORE_DIR` or `OMNIAGENT_DIR` if a checkout is elsewhere.

## See Your Run Beside the Protocol

`make demo` runs the Petstore order flow against fresh servers, captures the sandbox's trace of every message, and writes `demo/live.html`: the [AAuth walkthrough](https://github.com/aistandardsio/agent-protocols) with this run's messages beside each step. Open it in a browser; it needs no server.

```bash
make demo             # Newman plays the agent
make demo-omniagent   # omniagent plays the agent; needs ANTHROPIC_API_KEY (or another model's key)
```

Each scenario the run performed appears as an "Observed" entry. Its steps show the real request and response, each token decoded (but not verified) with raw values masked, when each message happened, and the exchanges the protocol does not describe, such as servers fetching each other's keys, between the steps they fell between. A Concept / Observed switch shows the document's example instead. The run is matched to the steps by [pidl](https://github.com/grokify/pidl) with the binding in `bindings/sandbox-petstore.binding.json`.

The targets run pidl v0.10.0 with `go run` and fetch the AAuth document from the agent-protocols v0.9.0 release, so they need Go and network access but no checkouts of either; see [Regenerating](docs/setup.md#regenerating) to use other versions. `demo/` holds the raw trace, with real development tokens, and is not committed.

## Exploring Without Running Anything

Import the mock collection and create a Postman mock server from it. Each request returns the example response from the AAuth walkthrough. The mock mode signs nothing and checks nothing; it is for reading the flows.
